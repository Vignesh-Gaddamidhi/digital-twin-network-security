# Day 193: Simulation Event Streaming & Background Workers

## 1. Asynchronous Job Worker Lineage
Day 193 disconnects the FastAPI request/response loop from scenario duration:

[POST /api/v1/simulations/run]
│
▼
[Redis List: cybertwin:queue:simulation_jobs]
│ (Job ID generated; returns immediate 202 Accepted)
▼
[SimulationBackgroundWorker]
├── State: QUEUED ➔ RUNNING ➔ COMPLETED (or RETRYING ➔ FAILED)
└── Scenario Stepper generates CanonicalEvents
│
▼
[Redis Stream: cybertwin:stream:simulation]
│
▼
[SimulationEventConsumer]
│
▼
[Authoritative Digital Twin Engine]
│
┌───────┴────────────────────────┐
▼                                ▼
[PostgreSQL Database]       [WebSocket Gateway Broadcast]
(Audit & Event Record)       (Next.js :3000 Canvas Update)


## 2. Invariant Rules
1. **Simulation -> Redis -> Twin -> UI**: The simulation runner never writes directly to client sockets or frontend stores.
2. **Finite Retries**: Transient failures retry up to `maxAttempts=3` with exponential backoff before transitioning to `FAILED`.
3. **Traceability**: All events generated by a simulation task inherit the `jobId` as their `correlationId`.
